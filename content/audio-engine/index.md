The audio engine is the timing backbone of the game client. Its single job is to answer
one question with millisecond accuracy, thousands of times per second:

> **Which sample is audible right now?**

Everything else — decoding, resampling, device negotiation — exists only to make that
answer trustworthy. Note timing, judgement windows, and chart scrolling all read from
this one clock; if it lies, every one of them lies with it.

## Why not the Web Audio API

Web Audio is built for *playback*, not for *measurement*. `AudioContext.currentTime`
advances in block-quantised steps, `outputLatency` is unreliable across platforms, and
the whole graph lives on a thread the browser is free to throttle. In a rhythm game a
20 ms error is the difference between a "Perfect" and a "Good", so the engine pushes
audio out of the browser entirely and into a native Rust thread.

## The three-layer design

Each layer solves a different source of delay:

```
┌─────────────────────────────────────────────────────────────┐
│ Renderer                                                    │
│   AudioClock — local clock, zero IPC per frame              │
│     ↑ handshake + resync every 500 ms                       │
└─────────────────────────────────────────────────────────────┘
                        │ window.electronAPI.audio (contextBridge)
┌─────────────────────────────────────────────────────────────┐
│ Main process                                                │
│   ipcMain handlers → napi bindings                          │
└─────────────────────────────────────────────────────────────┘
                        │ N-API (napi-rs)
┌─────────────────────────────────────────────────────────────┐
│ rust-core                                                   │
│   decoder → device → engine, all reading one clock          │
└─────────────────────────────────────────────────────────────┘
                        │
                   OS audio (ALSA / PipeWire / CoreAudio / WASAPI)
```

1. **[[native-module|The native module]]** decodes the whole file to PCM on a worker
   thread and opens the output device asking for 256-frame buffers. The stream starts
   immediately, pushing silence — so the expensive device warm-up is paid at load time
   instead of on the first `play()`.

2. **[[playback-clock|The playback clock]]** anchors itself to the instant sample 0
   becomes *audible*, not to how many samples have been copied into the device buffer.
   It measures the sound card's real sample rate against the monotonic clock, so crystal
   drift does not accumulate over the length of a song.

3. **[[renderer-clock|The renderer clock]]** never asks the native side per frame. It
   estimates once — via an NTP-style handshake — the `performance.now()` value at which
   the song was at position 0. From then on, position is a local subtraction.

## Where the code lives

| Path | Role |
| --- | --- |
| `rust-core/src/audio/decoder.rs` | File → interleaved `f32` PCM |
| `rust-core/src/audio/device.rs` | Stream configuration, channel mapping, resampling |
| `rust-core/src/audio/clock.rs` | `PlaybackClock` — all timing state, in atomics |
| `rust-core/src/audio/engine.rs` | `AudioEngine` — owns the stream and its callback |
| `rust-core/src/lib.rs` | N-API bindings and the global engine handle |
| `electron/audio-channels.cjs` | IPC channel names, shared and dependency-free |
| `electron/audio-ipc.cjs` | Main-process handlers |
| `preload.cjs` | `contextBridge` → `window.electronAPI.audio` |
| `src/lib/audio/audio-clock.ts` | Renderer-side `AudioClock` |
| `src/lib/audio/types.ts` | Bridge types and the `Window` global |

## Building

```bash
pnpm install
pnpm run build:native     # compiles rust-core (needs cargo)
pnpm run test:native      # unit tests for channel mapping and resampling
pnpm run electron         # vite build + Electron
```

For renderer work with hot reload, in two terminals:

```bash
pnpm run dev
pnpm run electron:dev
```

The compiled addon is platform-specific and not committed, so `build:native` has to run
once on any new machine. `rust-core/index.d.ts` *is* generated by the same command,
straight from the Rust doc comments, and is the authoritative description of the surface.

## Measured behaviour

Taken on one Linux machine, playing a 44.1 kHz stereo track through the default device:

| Metric | Value |
| --- | --- |
| `load()` — decode plus device open | ~550 ms for a 10-minute track |
| `play()` → first audible sample | ~22 ms |
| `restart()` → position reads 0 | immediate |
| Output latency reported by the backend | ~14 ms |
| Position drift against the monotonic clock, over 90 s | none measurable |

> [!warning] These numbers are one data point
> They come from a single machine, one device, and one backend. `load()` scales with
> track length. Output latency in particular varies enormously with the device path —
> the same machine through a different backend reports ~3.5 ms — and macOS (CoreAudio)
> and Windows (WASAPI) have not been characterised at all.
